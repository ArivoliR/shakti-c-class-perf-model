\section*{Executive Summary}

The current dual-issue SHAKTI model predicts 10,589,781
cycles and IPC 1.2060 on the generated dual CoreMark
trace window. The clean dual RTL ground truth is 10,398,758
cycles and IPC 1.22817; the cycle-stamped run reproduced
those app-log counters exactly, so the trace instrumentation is non-perturbing.

\textbf{Validation gate status: not passed.} The dual baseline now has a real
per-instruction $\Delta t$ comparison against RTL, not a proxy. Its accuracy is
93.302\%
(11,915,999/12,771,407
matching inter-commit deltas), with aggregate cycle error
1.837\%. This is below the 97\%
Phase-1 gate, so the architectural experiments below are useful directional
signals but still carry the measured residual timing error.

The backpressure blind spot that motivated this round is fixed for aggregate
cycle deltas: the depth-1 s3/s4, s0/s1, s1/s2, and s4/s5 RTL slowdowns are now
predicted within a few percent. However, local $\Delta t$ cadence is still weak
for the front-end depth-1 Dhrystone points, so this is not a full mechanism-level
closure.

A single-issue floating-point validation addendum now closes the integer-only
hole in the validation set. A new dense FP benchmark has 28.575\% FLOAT
instructions in its measured window. Before FP timing was modelled, the
single-issue model reached only 64.612\% $\Delta t$ accuracy on that trace; after
adding source-derived FPU latency it reaches 99.863\%, with -0.063\% aggregate
cycle error.

The second memory port alone helps only modestly in this model:
+0.698\%. Intra-bundle ALU forwarding is
the largest individual gain. The best draining two-issue combination found is
E+H: intra forwarding + branch, with IPC 1.2953
(+7.406\%
versus baseline). The quad approximation did not complete/drain in the full-trace sweep and is reported as not completed, not as a measured null. The model-owned branch+branch
opportunity count is much smaller than the defective RTL event-52 story suggests.

\subsection*{Single-Issue Floating-Point Validation}

The prior holdout set was entirely integer. Dhrystone and CoreMark contain no
dynamic FLOAT instructions in the measured windows, so the FPU path had not been
validated. I added \texttt{benchmarks/fpbench/}, a self-contained dense double
matrix kernel, instead of importing Whetstone. The reason was practical:
\texttt{fpbench} uses no libm, has no host-dependent timing harness, and keeps
FP work from being constant-folded with volatile matrices and a checksum.

Two independent baseline simulator runs both measured 1,646,171 cycles and
739,818 retired instructions for \texttt{ITERATIONS=100}. The measured window's
decoded mix is:

\begin{tabular}{@{}lrr@{}}
\toprule
FU class & Instructions & Share \\
\midrule
ALU & 354,709 & 47.945\% \\
FLOAT & 211,400 & 28.575\% \\
MEMORY & 115,204 & 15.572\% \\
BRANCH & 58,500 & 7.907\% \\
\bottomrule
\end{tabular}

The FLOAT sub-ops are 211,300 FMA-path operations
(\texttt{fmadd}, \texttt{fadd}, \texttt{fsub}, \texttt{fmul}) and 100
integer-to-float conversions, so the benchmark exercises the normal FP datapath
rather than accidentally compiling to soft-float.

\paragraph{FPU timing.}
The single-issue makefile defines \texttt{spfpu} and \texttt{dpfpu}, but not
\texttt{hardfloat}; \texttt{src/fpu/fpu.bsv} therefore instantiates
\texttt{fpu\_bsvfloat}. The model now detects this from \texttt{makefile.inc}.
For a hardfloat build it reads \texttt{fma\_stages}, \texttt{ftoi\_stages},
\texttt{itof\_stages}, and \texttt{ftof\_stages} from
\texttt{src/fpu/fpu.defines}. For the active \texttt{bsv\_float} build, the FMA
path is five cycles: one top-level input FIFO cycle plus the four explicit
\texttt{fpu\_fm\_add\_sub} state-machine stages before the result is visible.
The FPU ready signal lags the result by one cycle because it observes
\texttt{rg\_multicycle\_op} and \texttt{ff\_input.notEmpty}.

\paragraph{Dual-issue FLOAT pairing.}
The dual-issue source was checked read-only. \texttt{stage2.bsv} allows
\texttt{ALU+FLOAT}, \texttt{FLOAT+ALU}, \texttt{CONTROL+FLOAT}, and
\texttt{FLOAT+CONTROL}, where CONTROL is \texttt{BRANCH}, \texttt{JAL}, or
\texttt{JALR}. \texttt{FLOAT+FLOAT} and unlisted scarce-FU combinations fall
through to single issue. The model's FLOAT pairing whitelist matches the RTL
source, but there is still no dynamic dual-issue FP validation trace.

\section*{Analysis}

Run A, the second memory port, improves IPC by +0.698\%.
It removes the modeled non-RAW mem+mem reject counter, but the speedup is much
smaller than a first-order lost-slot estimate. The measured interaction is
sub-additive, not lockstep-gated: A+B is smaller than A plus B, so those changes
remove overlapping bubbles rather than unlocking one another.

Run B improves IPC by +0.689\%, confirming
that stage3/stage4 coupling is a real limiter. Run C is sub-additive relative to
A+B, so the second memory port and decoupling overlap in the bubbles they remove.

Run E is the largest individual improvement at +6.237\%.
It directly attacks the RAW rejection class and roughly halves the modeled RAW
reject count. This is the strongest candidate for RTL work if its implementation
cost is manageable.

Run H gives only +0.480\%. The model's
independent branch+branch opportunity count is 159,885
on CoreMark, so branch+branch is not the dominant issue in this trace. This is
also a useful independent replacement for the defective RTL event 52.

The automatic stacked run I reached IPC 1.2756.
The extra probes show why it is not the actual best: A+E reached IPC
1.2619, while
E+H reached IPC 1.2953.
So the second memory port interferes with the intra-forwarding win in this trace,
whereas branch+branch is mildly complementary with intra-forwarding.

\section*{What Did Not Work}

\begin{itemize}
\item Independent retire alone had no effect because actual lockstep stage4
already delivers paired slots to stage5 together.
\item The branch next-PC relaxation is unresolved: the named F config remains
an exact no-op in this model and should not be treated as RTL evidence.
\item Symmetric slots remains an exact no-op in this trace/model. Treat it as an
unexpressed hypothesis, not proof that the RTL change is worthless.
\item Combining decoupled lockstep with intra-bundle forwarding did not drain on
a 100k-instruction diagnostic run. The final best combination therefore excludes
B when E is selected; this is reported as a model limitation/negative
interaction, not hidden.
\item Quad issue did not complete/drain in the full-trace sweep. It is reported
as not completed rather than as a measured null.
\end{itemize}

\section*{Recommendations}

\begin{enumerate}
\item Prototype intra-bundle ALU forwarding first. Estimated standalone gain:
+6.237\%; rough RTL cost: medium
(operand muxing, bypass select, verification of RAW edge cases).
\item Combine intra-bundle ALU forwarding with a second branch unit only if the
branch hardware is cheap. Best measured combination: E+H at IPC
1.2953.
\item Treat the second memory port as a secondary change, not the headline by
itself. Estimated standalone gain: +0.698\%;
rough RTL cost: high (D-cache/store-buffer/arbiter integration). It regresses
the E combination, so do not prioritize it before validating with a dual trace.
\item Investigate lockstep decoupling separately from intra-forwarding.
Estimated standalone gain: +0.689\%;
rough RTL cost: medium-high because it touches stage3/stage4 valid/ready and
commit bookkeeping.
\item Deprioritize branch+branch hardware until a corrected RTL counter or dual
trace says otherwise. Estimated gain: +0.480\%;
rough RTL cost: medium.
\item Do not commit to quad issue from this evidence. The current approximation
did not drain on the full trace and is not a validated 4-wide front end.
\end{enumerate}

\section*{Limitations}

The model is a timing model over an already committed dynamic trace. It does not
compute data values. The validation set now covers small-footprint,
cache-resident integer code plus one dense floating-point arithmetic kernel. It
still does not model data-cache misses, cache conflicts, instruction-cache
misses, wrong-path fetch bandwidth, FP divide/sqrt data-dependent special cases,
or CSR/trap behavior that depends on values. The dual CoreMark trace now
provides per-instruction RTL commit cycles, but the baseline model only reaches
the accuracy reported above; the residual mismatches are concentrated around
multiply-heavy and control-flow neighborhoods and should be diagnosed before
treating the experiment deltas as RTL-commitment evidence. A Dhrystone commit
trace is still missing for held-out dual-issue $\Delta t$ validation, and no
dynamic dual-issue FP trace exists yet.
